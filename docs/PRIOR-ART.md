# Prior art, and what Chart took from it

Two projects were read while designing the rule language. Both are **enforcement**
systems — they sit between an agent and its tools and can refuse a call — while
Chart is an **observer**. That difference decides most of what follows: the
borrowable part is the *vocabulary and the record discipline*, not the actions.

- `agent-policy-gateway` (Python) — a reference monitor with declarative YAML
  policies, taint/IFC, session call history and a hash-chained audit log.
- `agent-governance-toolkit` / ACS (Microsoft) — a portable policy *contract*:
  intervention points, snapshots, a closed verdict set, a stateless deterministic
  runtime.

---

## 1. Taken

### 1.1 Chain conditions → our `window`

The gateway's `chain: { any_prior, no_prior }` asks "has any recorded call
matching X already happened?", with `fnmatch` globs over tool name, resource and
output label:

```yaml
when:
  tool: send_money
  chain:
    any_prior:
      - source: "eval:untrusted"
        verdict: allow
```

This is the cheapest useful form of "look at history", and it is already
expressible in Chart with the existing window — worth noting because it validates
the primitive:

```jsonc
{ "window": { "events": { "type": ["command"], "where": { … } },
              "measure": "count", "op": "gte", "value": 1 } }   // any_prior
{ "window": { … , "measure": "count", "op": "eq", "value": 0 } } // no_prior
```

**Nothing new was added for this.** The gateway's contribution was confidence
that "history as a query" is the right shape, and that it needs no state.

### 1.2 fnmatch on arbitrary strings

The gateway globs tool names (`get_*`) and resources (`https://*`), not just file
paths. Chart's `glob` did `*`, `**`, `?` for paths; it now also does `[abc]`,
`[!abc]` and `\` escapes, and is documented as working on any string
(`payload.command`, `payload.tool`, a process name).

### 1.3 Hash-chained record

The gateway writes an append-only audit log where each record carries the digest
of the previous one (`prev`), with a `verify-chain` command. Chart's
`FindingRecord` now does the same: `prev` + `digest`, and `verifyChain()` reports
the first broken link. Same reason: the record is the thing a report is rendered
from, so a quietly edited record makes every past report a lie.

Difference: theirs is a security control with a reviewer in mind; ours is
tamper-*evidence* for a report a human is about to trust. Ours is a 128-bit
non-cryptographic digest, and the docs say so — it catches corruption and casual
edits, not an attacker who can rewrite the whole log.

### 1.4 Closed reason vocabulary

ACS keeps `reserved-reasons.json`: a closed set of reason identifiers, so a
verdict is machine-comparable. Chart now has `src/regimen/reasons.ts`: the twelve
reserved slugs (Absence's own vocabulary), plus a namespaced escape
(`user.flapping`) for rules that need their own key. Validation rejects anything
else.

### 1.5 Mode naming: `evaluate_only` vs `enforce`

ACS makes "do not act" a *mode of the evaluation request*, and requires it to be
visible. Chart's observe / replay / simulate split is the same idea; the naming
was tightened after reading it — a simulation is labelled `hypothetical: true`
rather than described in prose.

### 1.6 Intervention points, as a closed enum

ACS judges at named points (`input`, `pre_tool_call`, `post_tool_call`,
`output`), each with a complete snapshot, and the runtime reads **only** that
snapshot. Chart's `phase: live | settled` is a coarser version of the same idea;
the lesson taken was the discipline — a closed set of judging moments, and an
explicit context per moment — rather than the specific list.

### 1.7 Fail-open vs fail-closed

The gateway's posture is "fail closed on audit": if a decision cannot be logged,
the action does not happen. Chart is the opposite for *rules* — a broken rule must
never hide the run — and the same for the *record*: if the findings cannot be
recorded, the judgement did not happen. Writing both postures down (DESIGN §5)
came from seeing theirs stated so plainly.

### 1.8 Numbers pinned by tests

Both projects pin their claims with measured matrices regenerated by one command.
Chart's analogue is the parity harness: 534 archived runs through both engines,
identical verdicts, run by `check:offline`.

## 2. Not taken, and why

| Idea | Why not |
|---|---|
| **Enforcement / `allow` / `deny` / `transform`** | Chart is an observer by design: it has no action layer, and adding one costs replay, neutrality and comparability (DESIGN §4). The gateway is the right place for that, and it already exists. |
| **Taint / information-flow control** | It needs to see data flowing between a tool's output and the next call's arguments. Chart *does* observe both, so a taint-like fact is technically possible — but it would make Chart half a semantic engine, and the ground truth would be a guess about which argument came from which output. Declined, and noted as the real limit of "observe only". |
| **`escalate` → deny + approval block** | Needs an approval channel; Chart has none. |
| **Rego / Cedar policy languages** | They would break the two properties the editor depends on: a rule validated *before* it runs, and a rule rendered as a row a human can read. |
| **YAML** | JSON is machine-diffable, which matters more here than YAML's comments. |
| **First-match ordering** | Chart is a lens: every matching rule contributes a finding, and the verdict is the loudest. Only `suppresses` carries firewall semantics. |
| **Declassification grants** | Interesting — "a later event clears an earlier finding" — but findings are immutable in the record. Deferred, not rejected. |
| **Full temporal logic** | DESIGN §3: the ladder stops at bounded sequences. |

## 3. What this changed in Chart

| Change | Where |
|---|---|
| `sequence` leaf — ordered steps, bounded gaps, leftmost and counted | `src/regimen/sequence.ts`, RULES §4 |
| fnmatch classes and escapes in `glob` | `src/facts/glob.ts` |
| closed reason vocabulary + normalisation | `src/regimen/reasons.ts` |
| hash-chained `FindingRecord` + `verifyChain` | `src/regimen/record.ts` |
| the ladder written down, with the three guard rails | DESIGN §3 |
| fail-open for rules vs fail-closed for the record | DESIGN §5 |
| sequence editor in the web UI | `web/src/components/Conditions.tsx` |

`example.flapping` is the payoff: "failed → recovered → failed again, within 30
events and ten minutes" is now twelve lines of user JSON rather than a fact the
engine would have had to know about.
